# Product Brief

## One-Liner

서비스명은 `코어블SAF`이다.

Coreable이 재고를 직접 보유하지 않는 단일 판매자 쇼핑몰.

## Problem

운영자는 상품을 직접 판매하고 싶지만, 물류와 출고는 공급처에 맡기고 싶다. 고객은 일반 쇼핑몰처럼 상품을 보고 결제하지만, 운영자는 주문 이후 공급처에 발주하고 배송 정보를 입력해야 한다.

이 모델에서는 공급처 품절, 출고 지연, 가격 변경 같은 운영 리스크가 발생한다. 따라서 시스템은 단순한 상품 판매 화면이 아니라 주문 이후의 상태 관리와 예외 처리까지 지원해야 한다.

## Target Users

### Customer

- 상품을 보고 구매하는 일반 고객
- 주문 상태와 배송 정보를 확인하고 싶은 고객
- 취소 또는 환불을 요청하는 고객

### Operator

- 기존 상품을 등록하고 전체 판매 상태를 관리하는 운영자
- 기존 수동/Domeggook 주문을 공급처에 발주하는 운영자
- 송장번호, 품절, 취소, 환불을 처리하는 운영자

### Supplier Manager — `B-100`~`B-105` Implemented

- Coreable 승인을 받고 이메일 초대로 연결된 공급처 담당자
- 자기 공급처의 상품, 옵션, 재고와 입금확인 완료 출고 요청만 처리하는 담당자
- 공급가와 출고 사실은 입력하지만 고객 판매가, 결제, 환불, 클레임 결정을 할 수 없는 담당자

## Core Principle

결제 완료와 공급처 발주 완료는 같은 사건이 아니다.

시스템은 다음 상태를 분리해서 관리해야 한다.

- 고객 결제 상태
- 내부 주문 상태
- 공급처 발주 상태
- 배송 상태
- 취소/환불 상태

## Operating Assumptions

- Coreable은 상품을 판매하지만 자체 재고를 보유하지 않는다.
- 기존 수동/Domeggook 상품은 실제 재고 수량을 관리하지 않는 `UNTRACKED` 모델을 유지한다.
- 신규 공급처 포털 상품은 공급처가 개별 등록하고 옵션별 수량을 관리하는 `TRACKED`를 기본으로 하되 명시적으로 `UNTRACKED`를 선택할 수 있다. 기존 상품을 소급 전환하지 않는다.
- 고객에게는 재고 모드나 `무제한` 문구를 노출하지 않고 구매 가능 여부만 보여준다.
- 주문 후 공급처 품절이 확인될 수 있다.
- 공급처 품절 시 고객에게 안내하고 해당 배송 그룹 주문 단위로 환불 처리한다.
- 도매꾹 source snapshot이 있는 주문은 입금확인 후 Private API로 자동 발주하고 배송 정보를 동기화한다. 그 외 기존 주문의 발주와 송장 입력은 관리자가 수동 처리한다.

## MVP Boundary

### Customer Scope

- 고객 로그인 화면은 카카오 소셜 로그인만 제공한다.
- 기존 Google/Naver OAuth 백엔드는 계정 호환을 위해 유지한다.
- 비회원 주문과 이메일/비밀번호 로그인은 제공하지 않는다.
- 고객은 상품 목록, 상품 상세, 장바구니, 주문서, 결제, 주문 내역, 배송 상태를 사용할 수 있다.
- 고객은 출고 전 취소를 요청하고 배송 후 반품/교환/환불 클레임을 접수할 수 있다.
- 결제는 계좌입금과 관리자 입금확인만 제공한다. PG 결제는 도입하지 않는다.
- 고객에게 별도 배송비를 청구하지 않는다. 공급처 배송비는 운영비로 처리하고 상품 판매가 계산에는 더하지 않는다.
- 여러 배송 그룹 상품을 한 번에 결제할 수 있지만, 주문은 배송 그룹별로 분리된다.

### Admin Scope

- 관리자는 DB에 등록된 소셜 로그인 계정만 접근할 수 있다.
- 관리자는 상품, 옵션, 이미지, 상품 상세 HTML/이미지 블록, 판매 상태를 관리할 수 있다.
- 관리자는 결제 완료 주문을 공급처 발주 대기 큐에서 확인하고 자동 발주 결과와 수동 발주 대상을 함께 처리한다.
- 관리자는 공급처 발주 시작, 공급처 발주 완료, 품절, 송장 입력, 배송 수동 보정, 취소/환불/반품/교환 클레임 처리를 수행한다.
- 관리자는 임의 상태값을 직접 쓰지 않고 허용된 액션과 상태 전이표를 통해서만 주문을 진행한다.
- 주문 상태 변경, 입금 불일치, 미완료 환불, 배송 수동 보정, 관리자 정정은 사유와 이력을 남긴다.

### Supplier Portal Scope — `B-100`~`B-105` Implemented

- Coreable은 고객 계약의 단일 판매자로 남고 결제, 환불, CS, 클레임 결정과 고객 판매가를 통제한다. 공급처 포털에는 판매자 정산이 없다.
- 비로그인 공급처 신청을 Coreable이 승인한 뒤 신청 연락 이메일로 1회용 초대를 보낸다. 링크 교환으로 이메일 소유를 검증하고 Kakao로만 담당자를 연결하며, 공급처당 활성 담당자는 1명이다.
- 첫 상품 기능은 개별 등록이다. 공급처 화면은 `상품 등록` 한 번으로 분류까지 끝내며 별도 승인 요청 단계를 요구하지 않는다. 무옵션 상품도 내부적으로 `기본` 옵션 하나를 만들고, 공급처는 공급가를 입력하지만 고객 판매가는 Coreable 가격 정책으로 서버가 계산한다.
- 구조와 판매 준비 조건을 만족한 일반 상품은 자동 공개하고, 인증·카테고리·법정 필수정보처럼 사람 판단이 필요한 상품만 Coreable 검토로 보낸다.
- 신규 포털 옵션은 `TRACKED`가 기본이고 `UNTRACKED`를 선택할 수 있으며, 기존 상품 옵션은 `UNTRACKED`로 유지한다. Checkout은 `TRACKED` 재고를 24시간 예약하고 만료 시 자동 해제하며, `EXPIRED` 뒤 확인된 정확한 금액의 입금은 모든 재고를 원자적으로 재확보한 경우에만 승인한다. 실패하면 배송 그룹별 환불 요청을 자동 생성하고 정상 주문으로 재개하지 않는다. 미입금 `CANCELLED` 뒤 확인된 입금은 정확한 금액이어도 전액 환불 후 새 checkout을 요구하며, 금액 불일치는 실제 수령액의 `PAYMENT_GROUP` Refund 한 건으로 반환한다.
- 포털 주문은 입금확인 성공 즉시 별도 수락 단계 없이 공급처 출고 요청으로 노출하고 배송지를 잠근다.
- 공급처 주문 목록에는 고객 개인정보를 넣지 않고, 상세에는 자기 배송에 필요한 최소 수령 정보만 기한을 두고 제공한다.
- Implemented B-104에서 공급처는 여러 송장에 주문 항목별 수량을 할당할 수 있다. 송장 등록은 실제 출고와 분리된 `TRACKING_REGISTERED`이며 서버가 4개 지원 택배사의 공식 배송조회 링크를 만든다. 고객은 `송장 등록 · 배송조회 가능`으로 보고, 공급처는 배송완료 전 택배사·송장을 정정하며 allocation 오류는 void 후 재등록한다. Coreable은 void·배송완료 증적과 제한된 배송완료 오보정을 관리하며 실시간 택배사 API는 사용하지 않는다.
- VOIDED 포함 송장이 한 번도 등록되지 않은 경우에만 배송 그룹 전체 품절을 보고할 수 있다. 공급처는 사실만 기록하고 환불 승인·거절·완료는 Coreable만 수행한다.
- 공급처 운영 알림은 이메일만 사용하며 제목, 본문과 발송 이력에 고객 이름, 전화번호, 주소, 배송 메모, 결제·환불 정보를 넣지 않는다.
- 기존 수동/Domeggook 상품·재고·발주·단일 송장 동작과 API는 호환 경로로 유지한다.

### Non-Goals

- 판매자 입점형 마켓플레이스와 판매자 정산 시스템은 만들지 않는다.
- 기존 수동/Domeggook 상품을 실제 재고 관리로 소급 전환하거나 실시간 공급처 재고 API를 연동하지 않는다. 신규 포털 상품의 `TRACKED` 재고는 예외다.
- 비회원 주문, 이메일/비밀번호 로그인, 계정 병합은 제외한다.
- 카드, 간편결제, PG 계좌이체·가상계좌, 휴대폰 결제, 상품권 결제는 제외한다.
- 배송 그룹 주문 내부의 상품, 옵션, 수량 단위 부분 취소/부분 환불은 제외한다.
- 기존 수동/Domeggook 주문의 부분 출고·분할 배송과 물류센터/WMS 연동은 제외한다. 신규 포털 주문의 수량 할당형 복수 송장은 예외다.
- 쿠폰, 포인트, 리뷰, 고급 검색, AI 추천, 모바일 앱은 제외한다.
- 공급처 운영 알림에는 문자, 카카오 알림톡, 앱 푸시를 사용하지 않는다. 기존 고객 거래 알림 정책은 변경하지 않는다.

### Launch-Blocking Checks

- 실제 약관, 개인정보처리방침, 배송/취소/환불 정책 문구는 출시 전 최종 검토가 필요하다.
- 사업자등록번호, 통신판매업 신고 면제 상태, 대표자, 주소, 고객센터, 개인정보 보호책임자 등 사업자 고시 정보가 실제 화면과 일치해야 한다.
- 계좌입금 구매안전서비스와 현금영수증 발급 절차가 준비되어야 한다.
- 개인정보 처리 위탁처, 제3자 제공 여부, 보존 기간, 마케팅 수신 동의 문구가 실제 운영 기준과 일치해야 한다.
- 도매꾹 자동 발주 주문의 배송 정보 동기화와 수동 송장 fallback을 실제 주문 1건으로 검증해야 한다.
- supplier portal production 활성화 전 외부 공급처 계약, 공급처·택배사 개인정보 제공 고지와 실제 초대/운영 이메일 전달을 검증해야 한다.
- `APP_SUPPLIER_PORTAL_ENABLED`는 B-100~B-105가 구현된 뒤에도 B-098 계약, privacy/live-email 및 inventory checkout release gate가 모두 준비될 때까지 production 기본값 `false`를 유지해야 한다.

## Success Criteria

- 고객이 상품을 선택하고 결제까지 완료할 수 있다.
- 관리자가 결제 완료 주문을 놓치지 않고 공급처 발주 대상으로 확인할 수 있다.
- 공급처 품절 시 주문을 품절 상태로 전환하고 환불 흐름으로 보낼 수 있다.
- 송장번호 입력 후 고객이 배송 상태를 확인할 수 있다.
- 주문, 결제, 발주, 배송, 환불 상태가 서로 섞이지 않는다.
- Implemented B-101 공급처 포털은 일반 상품을 별도 수동 승인 없이 공개하고 위험 상품만 Coreable 검토 대상으로 분리한다. Production feature flag는 나머지 release gate가 끝날 때까지 닫아 둔다.
- Implemented B-102 예약 재고, B-103 최소 개인정보, B-104 복수 송장 할당과 B-105 송장 전 품절·클레임 사실 입력은 기존 주문 흐름과 Coreable 환불 권한을 유지한다.
