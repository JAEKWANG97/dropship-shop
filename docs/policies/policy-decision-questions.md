# Policy Decision Questions

이 문서는 정책을 하나씩 확정하기 위한 질문 목록이다.

## Step 1: Account

1. 비회원 주문을 허용할 것인가? Confirmed: 허용하지 않는다.
2. 로그인은 이메일/비밀번호로 시작할 것인가? Confirmed: 고객 로그인은 이메일/비밀번호를 제공하지 않는다.
3. 소셜 로그인은 MVP에 포함할 것인가? Confirmed: 카카오, 구글, 네이버만 제공한다.
4. 관리자 계정은 수동 생성으로 충분한가? Confirmed: DB에 등록된 소셜 계정만 관리자 권한을 가진다.

## Step 2: Catalog And Inventory

1. 실제 재고 수량을 관리하지 않는다는 전제를 확정할 것인가? Confirmed: 실제 재고 수량은 관리하지 않고 판매 상태만 관리한다.
2. 옵션 단위 품절을 허용할 것인가? Confirmed: 상품 상태와 옵션 상태를 분리한다.
3. 상품 상세는 어떤 형식으로 작성할 것인가? Confirmed: IMAGE + HTML 블록 방식으로 작성한다.
4. 상품 이미지는 최대 몇 장까지 허용할 것인가? Confirmed: 대표 1장, 갤러리 최대 10장, 상세 블록 이미지 최대 50장, 이미지당 최대 10MB.
5. 공급처 가격 변경 시 기존 결제 완료 주문은 어떻게 처리할 것인가? Confirmed: 결제 완료 주문은 결제 당시 가격을 유지하고, 상품 가격 변경은 새 주문부터 적용한다.

## Step 3: Order

1. 주문은 결제 전에 생성할 것인가? Confirmed: 입금 안내 전에 `PAYMENT_PENDING` 주문을 먼저 생성한다.
2. 결제 대기 주문은 얼마 뒤 만료할 것인가? Confirmed: 계좌입금 MVP는 기본 24시간 입금 기한을 두고 관리자 미입금 취소로 종료한다.
3. 배송지 변경은 어느 상태까지 허용할 것인가? Confirmed: 결제 후에는 `SUPPLIER_ORDER_PENDING` 상태이면서 `addressLockedAt`이 비어 있는 주문에만 고객 직접 변경을 허용한다.
4. 고객에게 내부 주문 상태를 그대로 보여줄 것인가? Confirmed: API는 안정적인 상태 코드를 내려주고, 고객용 표시 문구는 프론트엔드에서 매핑한다.

## Step 4: Payment

1. 결제는 무엇으로 제공할 것인가? Confirmed: 계좌입금과 관리자 입금확인만 제공한다.
2. 현재 제외하는 결제 수단은 무엇인가? Confirmed: 카드, 간편결제, PG 계좌이체·가상계좌, 휴대폰 결제, 상품권 결제는 도입하지 않는다.
3. PG 가상계좌는 제공할 것인가? Confirmed: 현재 제외하고 구매안전서비스와 함께 재검토한다.
4. 금액 불일치 시 자동 취소할 것인가, 수동 검토할 것인가? Confirmed: 주문을 확정하지 않고 취소 또는 수동 검토 대상으로 둔다.
5. 부분 취소를 MVP에서 지원할 것인가? Confirmed: 배송 그룹 주문 단위 부분 취소/부분 환불은 지원하고, 상품/옵션/수량 단위 부분 취소/부분 환불은 MVP에서 제외한다.
6. 결제 실패/만료 주문을 고객 주문 내역에 노출할 것인가? Confirmed: 고객 주문 내역에 노출하지 않는다.

## Step 5: Fulfillment And Shipping

1. 공급처 발주는 관리자 수동으로 시작할 것인가? Confirmed: MVP에서는 관리자가 공급처에 수동 발주한다.
2. 배송비는 고정 배송비인가, 일정 금액 이상 무료인가? Confirmed: 고객에게 별도 배송비를 청구하지 않고 상품 가격에 배송비를 포함한다.
3. 한 주문에 여러 공급처 상품이 섞이는 것을 허용할 것인가? Confirmed: 한 주문은 하나의 배송 그룹만 포함하고, 배송 그룹은 같은 공급처 기준으로 나눈다.
4. 배송 완료는 수동 처리할 것인가, 택배 조회 연동까지 할 것인가? Confirmed: MVP에 택배사 자동 배송조회 연동을 포함한다. 단, 관리자 수동 보정도 지원한다. 구현 방식은 별도 기술 조사 후 결정한다.

## Step 6: Cancellation And Refund

1. 공급처 발주 전 고객 직접 취소를 허용할 것인가? Confirmed: `SUPPLIER_ORDER_PENDING` 상태이면서 공급처 발주 작업이 시작되지 않은 주문에만 고객 직접 취소를 허용한다.
2. 공급처 발주 후 취소는 관리자 승인으로 처리할 것인가? Confirmed: 공급처 발주 작업 시작 후 배송 전 취소는 취소 클레임으로 접수하고 관리자 수동 심사로 둔다.
3. 부분 품절은 전체 취소/환불로 처리할 것인가? Confirmed: 특정 배송 그룹 주문 품절은 해당 배송 그룹 주문만 취소/환불하고, 배송 그룹 주문 내부 일부 품절은 해당 배송 그룹 주문 전체 취소/환불로 처리한다.
4. 배송 후 반품/교환은 MVP에서 어디까지 지원할 것인가? Confirmed: 자동 처리 없이 클레임 접수와 관리자 수동 심사로 둔다.
5. 반품/교환 접수 기간은 어떻게 둘 것인가? Confirmed: 단순 변심은 배송 완료일로부터 7일, 판매자 귀책 클레임은 배송 완료일로부터 3개월 이내이면서 인지일로부터 30일 이내로 둔다.
6. 반품/교환 배송비는 누가 부담할 것인가? Confirmed: 단순 변심은 고객 부담, 상품 하자/오배송/상품 정보와 다름/배송 문제는 운영자 부담을 기본으로 둔다.
7. 클레임 증빙은 어디까지 받을 것인가? Confirmed: 상품 하자, 오배송, 상품 정보와 다름, 배송 문제는 사진 증빙을 필수로 받는다.

## Step 7: Admin Operations

1. 관리자 권한을 하나로 둘 것인가, 역할을 나눌 것인가? Confirmed: MVP에서는 `ADMIN` 단일 역할로 시작한다.
2. 관리자 계정 생성은 어떻게 할 것인가? Confirmed: 별도 가입 화면 없이 DB seed 또는 수동 등록으로만 부여한다.
3. 주문 상태 변경 이력을 MVP부터 남길 것인가? Confirmed: 주문 상태 변경 이력은 MVP부터 기록한다.
4. 환불 처리에는 관리자 사유 입력을 요구할 것인가? Confirmed: 취소, 환불, 품절, 배송 수동 보정, 관리자 정정 액션은 사유 입력을 필수로 한다.
5. 잘못된 상태 변경을 되돌리는 기능이 필요한가? Confirmed: 자동 되돌리기 버튼은 제공하지 않고, 관리자 정정 액션과 이력으로 처리한다.
6. 상품 변경 이력은 어디까지 남길 것인가? Confirmed: 가격, 상품/옵션 판매 상태, 공급처 변경부터 MVP에서 기록하고 상세 콘텐츠 diff는 이후로 미룬다.

## Step 8: Legal And Customer Notice

1. 공급처 품절 가능성 고지는 상품 상세과 주문서 모두에 둘 것인가? Confirmed: 상품 상세와 주문서 모두에 고지한다.
2. 정책 페이지는 어디에서 접근 가능해야 하는가? Confirmed: 고객 메뉴와 푸터에서 이용약관, 개인정보처리방침, 배송 정책, 취소/환불 정책에 접근 가능해야 한다.
3. 주문서에서 정책 동의 체크박스를 둘 것인가? Confirmed: 결제 그룹(PaymentGroup)마다 1개의 통합 확인 체크박스를 둔다.
4. 정책 버전 관리를 MVP에 포함할 것인가? Confirmed: 정책 페이지는 버전/시행일을 가지고, 결제 그룹(PaymentGroup) 시점의 확인 정책 버전과 확인 시각을 저장한다.
5. 고객 알림은 무엇으로 시작할 것인가? Confirmed: 거래 SMS와 주문 상세 상태 표시로 시작하고, SMS를 사용할 수 없는 환경은 `SKIPPED` 이력을 남긴다.
6. 사업자 정보는 어디에 표시할 것인가? Confirmed: 푸터와 고객센터/회사 정보 페이지에 상호, 대표자, 사업자등록번호, 통신판매업 신고번호 또는 신고 면제 상태, 주소, 고객센터, 개인정보 보호책임자, 호스팅 제공자를 표시한다.
7. 개인정보 처리표는 어디까지 둘 것인가? Confirmed: 수집 항목, 처리 목적, 보유 기간, 처리 위탁처, 제3자 제공 여부를 행 단위로 관리한다.
8. 마케팅 동의는 거래 알림과 분리할 것인가? Confirmed: 주문, 배송, 결제, 환불, 클레임 알림은 거래 알림으로 처리하고 마케팅 알림은 채널별 선택 동의로 분리한다.
9. 회원 탈퇴 후 재가입은 어떻게 처리할 것인가? Confirmed: 탈퇴 계정은 비식별화하고 법정 보존 기록은 분리 보관하며, 같은 소셜 계정 재가입은 새 고객 계정으로 생성한다.
